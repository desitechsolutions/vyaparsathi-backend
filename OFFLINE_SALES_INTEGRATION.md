# Offline Sales Integration Guide

## Overview

The backend now provides complete offline sales queueing infrastructure. Frontend sends sales when offline, backend processes them asynchronously when the app comes online.

## Architecture

```
Frontend (Offline) → POST /api/sales/offline-queue → Backend (Queue)
                                                              ↓
                                                    Async Processor
                                                              ↓
                                    Create Sale + Generate Invoice
                                                              ↓
                                        Update Queue Status
                                                              ↓
Frontend (Polls Status) ← GET /api/sales/offline-queue/{clientTxnId}
```

## Status Workflow

```
DRAFT
  ↓ (when backend processes)
PENDING
  ↓ (deserializing + validating)
PROCESSING
  ↓ (creating sale + invoice)
COMPLETED ✓ (success)
FAILED (retryable)
CONFLICT (manual review needed)
```

### Status Meanings

| Status | Meaning | Retryable | Action |
|--------|---------|-----------|--------|
| DRAFT | Queued, not processed yet | - | Wait for PROCESSING |
| PENDING | About to process | - | Check soon |
| PROCESSING | Sale creation in progress | - | Check soon |
| COMPLETED | Sale + invoice created | No | Display to user |
| FAILED | Retriable error | Yes | Retry up to 3 times |
| CONFLICT | Duplicate detected (409) | No | Admin review |

## Error Handling

### 400 Bad Request
```json
{
  "error": "Invalid request",
  "message": "clientTxnId is required"
}
```

**Causes:**
- Missing clientTxnId
- Invalid shopId or userId (headers)
- Payload too large (>1MB)

**Fix:** Validate request before sending, add required headers.

---

### 409 Conflict (Duplicate Sale)
```json
{
  "status": "CONFLICT",
  "errorCode": "CONFLICT",
  "errorMessage": "Sale with this transaction already exists"
}
```

**Causes:** Frontend created sale twice (network retry).

**What Happened:** The first sale succeeded, second attempt detected as duplicate by backend.

**Fix:** This is handled! Frontend gets invoice from queue status, no manual action needed.

---

### 500 Internal Server Error
```json
{
  "error": "Internal Server Error",
  "message": "Failed to process sale"
}
```

**Causes:** 
- Invoice generation failed
- Database error
- Invalid inventory

**Fix:** Check backend logs, queue record marked as FAILED, will retry.

## Frontend Integration Checklist

### When App Comes Online
1. Call `GET /api/sales/offline-queue/shop/{shopId}/pending` to check pending count
2. If count > 0, call `POST /api/sales/offline-queue/shop/{shopId}/process`
3. Poll `GET /api/sales/offline-queue/{clientTxnId}` every 2 seconds for status
4. When status = COMPLETED:
   - Display invoice to user
   - Download from `invoiceSignedUrl`
   - Clear offline cache

### When User Creates Sale (Offline)
1. Generate `clientTxnId` (UUID v4)
2. Get `deviceId` from localStorage/IndexedDB
3. Call `POST /api/sales/offline-queue` with full sale data
4. Store response: `{ id, offlineSaleNo, clientTxnId }`
5. Print receipt with `offlineSaleNo` + "DRAFT - PENDING SYNC"
6. Save to IndexedDB for offline queue display

### When User Submits Payment (Offline)
Same as above - no changes needed.

## Processing Flow (Backend)

### Automatic Processing
1. Frontend calls `POST /api/sales/offline-queue/shop/{shopId}/process`
2. Backend spawns async task immediately (returns 202 ACCEPTED)
3. Async processor:
   - Fetches all DRAFT + FAILED (< 3 retries) sales
   - Deserializes `requestPayloadJson`
   - Validates data
   - Calls existing `RegistryService.createSale()`
   - Calls invoice generation
   - Updates queue record: status=COMPLETED, saleId, invoiceNumber
4. Frontend polls for status changes

### Fallback (Scheduler)
If frontend offline-sync fails:
- Server-side scheduler runs every 5 minutes
- Processes stuck queues automatically
- Cleanup runs daily at 2 AM (removes records >7 days old)

## Database Schema

```sql
CREATE TABLE offline_sales_queue (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  shop_id BIGINT NOT NULL,
  user_id VARCHAR(255) NOT NULL,
  client_txn_id VARCHAR(36) NOT NULL,
  device_id VARCHAR(255) NOT NULL,
  status VARCHAR(50) NOT NULL,
  offline_sale_no VARCHAR(255) NOT NULL,
  request_payload_json LONGTEXT NOT NULL,
  sale_id BIGINT,
  invoice_number VARCHAR(255),
  invoice_signed_url VARCHAR(2048),
  error_code VARCHAR(100),
  error_message VARCHAR(1000),
  retry_count INT DEFAULT 0,
  synced_at TIMESTAMP,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  
  UNIQUE KEY uk_shop_client_txn (shop_id, client_txn_id),
  INDEX idx_shop_status (shop_id, status),
  INDEX idx_user_status (user_id, status),
  INDEX idx_device_id (device_id),
  INDEX idx_created_at (created_at),
  INDEX idx_status (status),
  INDEX idx_sale_id (sale_id)
);
```

## Monitoring & Alerts

### Key Metrics
- **Pending Queue Size:** `GET /api/sales/offline-queue/shop/{shopId}/stats`
  - Alert if > 100 (processing backlog)
- **Failed Count:** `failed` from stats
  - Alert if > 10 (investigate cause)
- **Conflicted Count:** `conflicted` from stats
  - Alert if > 1 (manual review needed)

### Query Examples
```sql
-- Find stuck queues (PROCESSING > 5 minutes)
SELECT * FROM offline_sales_queue 
WHERE status = 'PROCESSING' 
AND updated_at < DATE_SUB(NOW(), INTERVAL 5 MINUTE);

-- Find sales that will be auto-deleted tomorrow
SELECT * FROM offline_sales_queue 
WHERE status = 'COMPLETED' 
AND synced_at < DATE_SUB(NOW(), INTERVAL 6 DAY);

-- List all device conflicts (duplicate sales)
SELECT device_id, COUNT(*) as count 
FROM offline_sales_queue 
WHERE status = 'CONFLICT' 
GROUP BY device_id 
HAVING count > 1;
```

## Troubleshooting

### Sale Stuck in PROCESSING
**Symptoms:** Status shows PROCESSING for > 5 minutes

**Cause:** Backend crash during processing

**Fix:** 
1. Check backend logs for errors
2. Manually trigger retry: `POST /api/sales/offline-queue/shop/{shopId}/process`
3. If persists, check database lock: `SELECT * FROM offline_sales_queue WHERE id = ?`

### Duplicate Sale (CONFLICT Status)
**Symptoms:** Two sales created with same clientTxnId

**Cause:** Race condition - frontend retried before first request completed

**Why This is OK:** Queue record tracks the first successful sale. Invoice is already generated.

**Fix:** Frontend fetches invoice from the successfully synced queue record.

### Invoice Not Appearing
**Symptoms:** Sale status = COMPLETED but invoiceSignedUrl is null

**Cause:** Invoice generation failed silently (bug in RegistryService)

**Fix:** Check backend logs, manually generate invoice, update queue record.

## Security Considerations

1. **Idempotency via clientTxnId:** Prevents double-charging on network retry
2. **Device ID Tracking:** Detects multi-device abuse (same user, different devices)
3. **Shop Isolation:** All queries scoped by shop_id + user_id
4. **No User Input in Payment:** Amount comes from inventory, not request
5. **Audit Trail:** All createdAt/updatedAt/createdBy tracked

## Performance Tuning

### Query Performance
- Indexes on (shop_id, status) for quick pending lookups
- Indexes on device_id for fraud detection
- Indexes on created_at for cleanup queries

### Async Pool
```
core_size: 2          # Min threads
max_size: 5           # Max threads
queue_capacity: 100   # Tasks queue before blocking
```

Tune via `spring.task.execution.pool.*` in application.properties

### Cleanup Strategy
- Records deleted after 7 days (configurable)
- Runs daily at 2 AM
- Can be triggered manually via API
